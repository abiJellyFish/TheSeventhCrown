# 前置知识

### Claude Code 能力框架
1. CLAUDE.md，项目说明书，每次会话自动加载
2. Hooks，特定时机触发的事件
3. Skills，按需加载的技能，包含 SOP
4. Plugins，插件，封装 skills + Hooks + MCP
5. LSP，代码导航（IDE）
6. MCP，连接外部工具和数据的协议
7. 子 Agent，并行执行任务，拥有独立上下文

- settings.json，标明白名单和黑名单操作，配置 hook
- .gitignore，注意密钥不提交

- Auto Memory：记录用户的习惯、反馈、经验。对话框输入 /memory，启用 Auto Memory
- 清空当前对话：/clear
- 压缩上下文：/compact
- 审查代码：/review
- 安全性审查：/security-review
- 优化代码：/simplify
- 进入只读规划模式：/plan
- 回滚（无法撤回终端命令）：rewind
- 选择历史会话：/resume
- 询问当前会话无关问题：/btw
- 子代理（SubAgent）界面：/agent

- 将任务分配给多个会话，比如拆分开发、审查、测试，注意避免同时修改导致冲突

### 上下文管理
上下文占用率超过 50% 时，会开始出现注意力稀释的情况。无关片段、失败动作会污染新对话。

- 将固定流程、重复的 Prompt 封装为 skill
- 上下文占用率超过临界值时，将上下文总结到一个交接文档 Progress.md 中。输入：
    将全部对话进展整理到 Progress.md 中，包含已经完成的事项、关键决策、未完成的待办。
    之后新开一个窗口或清空对话，读取 Progress.md 就能继续工作。保证持续维护 Progress.md 
- 频繁清空上下文，同一任务内压缩上下文或使用交接文档。
- 查找、调查任务分配 Subagents 完成，主会话接收结论。

### 将项目贡献到开源社区

用 ai 生成以下文件：
- README.md：项目介绍、功能截图、安装使用说明、环境搭建、技术栈
- LICENSE：开源协议（推荐 MIT 协议）
- .gitignore：确保不提交敏感信息
- Contributing 指南，告诉别人如何参与贡献

# 开发规范

Agent 工作循环：
    探索（已有文件和需求）-推理（分析问题和规划）-行动-反馈（测试并发现问题）

## 方案规划

AI 会优先让代码能跑起来，而不是让代码结构合理。一旦代码能运行，AI 就会倾向于在现有代码上打补丁，而不是重新设计。AI 倾向于局部正确，可能产生幻觉，AI 难以贴合业务需求。不提前规划好，ai就会让你知道什么叫欲速则一坨。做的越快，改的越多。
对话时赋予 ai 角色。规划时明确要求不修改文件。

让 ai 在开源平台找是否有现成项目作为参考。
Git 集成，确保出错能够回退。大幅改动前提交远程仓库、不同功能创建分支。

- 规划比执行更重要，开发之前明确（plan mode）：
    这个应用的核心功能是什么；用户会怎么使用它，使用的场景；哪些功能是必须的，哪些是可以以后再加的；有没有什么特殊的限制或要求；使用的框架、依赖库、技术栈。
可以表达想法，让 AI 提供方案

> 使用 `superpowers:brainstorming` （头脑风暴）技能

- SDD（规范驱动开发），开发前写明开发过程的规范。包含：
    功能需求、技术和制作方案、用户行为和边界、目标和验收标准、非功能规范（性能，安全，兼容性）。
    从规范推导技术方案、实施任务和测试，根据反馈的问题或在需求变化时持续同步规范。
    每个任务分别对应哪个需求，每条验收标准标明由哪些测试或检查证明。
    规范相当于稳定的项目记忆，避免上下文过长丢失关键约束。规范减少需求模糊和方向偏离。
    开发链路：规范、技术计划、任务、测试，互相可以追溯

    人负责确定问题，做业务需求和技术取舍，审查规范，处理冲突，验收。Agent负责拆解和实现，执行验证。

    SDD 流程：
    1. 需求文档
    - 自然语言写明功能和需求，包含目标、业务场景、边界、验收证据。
    - 消除歧义，比如模糊词汇、边界情况（失败，超时，重复，并发，权限）、需求冲突、约束、当前范围之外的
    2. 技术方案
    - 涉及的具体模块和边界。数据结构和接口。
    - 状态流转。异常恢复策略。
    - 测试方案和验收标准
    - 技术选型和理由
    3. 任务清单
    开发工作拆分为小任务，可以独立审查、测试，能够追溯到某条规范。
    ai 执行过程中，监督修改了哪些文件（diff），测试（单元测试，集成测试，端到端测试），是否遗留假设、失败测试、未完成项，能否追溯到验收标准（带证据），是否冲突（依赖关系）

    根据规范，审查除了代码本身，还可以检查：某个实现对应的需求、是否覆盖边界、某个测试对应的验收标准、修改是否超出范围
    如果开发过程发现原方案有问题，先更新规范设计，再重新执行

    SDD 模板（修改或新增功能）
    - 功能名称
    - 背景和目标、非目标
    - 场景：用户行为，系统反馈
    - 边界和异常
    - 技术约束：架构，接口，安全，性能，兼容
    - 验收标准：每条标准对应的测试和检查证据
    - 任务实施：拆分为小任务，可以独立实现、审查和验证。

    SDD 参考：GitHub Spec Kit、Kiro

1. PRD（产品需求文档），将想法转换为结构化的需求文档，包含：
    项目概述、目标用户、功能列表（优先级）、目标和标准、安全、性能、兼容性
2. SPEC（技术规范文档），描述开发方式，包含：
    系统架构（前后端交互）、技术和框架、数据模型（数据库表、字段、关系）、接口（RESTful）、文件结构
    可以让模型根据 PRD 制作 SPEC
3. API 接口文档
    RESTful设计，统一响应结构和错误码表；覆盖每一处数据点；SSE 接口写清事件类型和数据格式；每个接口要有完整请求/响应示例
4. 初始化 CLAUDE.md

根据编写完成的 SDD 文档，写一份完整的开发路线规划和项目架构。拆分多个步骤（前端、后端、数据库分离），每个步骤拆分多个 TODO 小任务列表，决定优先级并逐个实现。
做好约束和规范，持续维护和优化 ai 上下文。

> 使用 `grill-me` （审查计划）技能

> 在实际开发前，先根据当前目录的所有文档，制作一个简单的原型 demo，根据效果判断需求、技术、逻辑等是否合理，是否需要调整，通过原型回头修改项目文档。

    1. 步骤流程：
    - 从 MVP 最小原型验证技术合理性，到搭建完整框架，到逐步完善每个模块

    2. 每个阶段描述包含：
    - 方案和效果（效果图）

    - 背景和目标、非目标
    - 场景：用户行为，系统反馈
    - 影响范围分析（数据隔离，风险，调用方法，权限，回归测试）

    - 技术约束：架构，接口，安全，性能，兼容

> 用自然语言描述需求或提出修改时，ai 应该先将自然语言转换为专业语言（通用的固定名词，比如前端页面组件的名称），之后再进行修改。
> 修改原则是不要修改原本的要求，要符合原本的要求，或者有更好的替代方案，并且不要写死数值和字段，保证通用性和模块化。    

> 用户
    根据 迭代需求.md 编写 迭代方案.md ，包含：
    - 产生原因（如果是需要修复的问题）、方案和效果（效果图）
    - 影响范围分析（数据隔离，风险，调用方法，权限，回归测试）
    - 建立三层测试（当前模块，关联模块，业务闭环）

> 回归测试（Regression Testing）指在修改代码之后，重新运行已有的测试，确保改动没有影响之前已经正常工作的功能。

- 验收清单
> 监督：修改了哪些文件（diff），测试（单元测试，集成测试，端到端测试），是否遗留假设、失败测试、未完成项，能否追溯到验收标准（带证据），是否冲突（依赖关系）
> 审查：代码语法，不能破坏程序的模块化；业务问题，某个实现对应的需求、是否覆盖边界、某个测试对应的验收标准、修改是否超出范围。
> 如果开发过程发现原方案有问题，先更新 项目规划文档.md，再重新执行。根据反馈的问题或在需求变化时持续同步 项目规划文档.md。

- 复盘
> 遇到的问题、原因、解决方案要总结回 规范文档（项目规划文档.md） 中，比如具体在哪里出错的，再做一次任务如何保证不出错。之后复盘归纳成永久经验，用在之后的类似项目中。
