---

### 核心三层总结

| 层 | 做什么 | 单位 |
|----|--------|------|
| **钟摆层** | 统一计时、驱动周期事件 | `pendulum_count` |
| **curS 层** | 每个角色实际走过的里程累积，仅在移动时累加 | `curS_ticks ∈ [0, maxS×SCALE)` |
| **移动层** | 选移动时 curS 跨过整数线 → crossed 格 → 寻路 → 执行 | `crossed = new_tiles − old_tiles` |

### 两套时间推进路径对比

| | 移动路径 | 行动路径 |
|----|----------|----------|
| 触发 | 方向键 | 休息/技能/交互命令 |
| 钟摆推进 | pendulum_acc_ticks 碎片累加，逐步推进 | pendulum_acc_ticks += cost × SCALE，统一走碎片路径 |
| NPC 结算 | 每钟摆 advanceNPCs(1.0)，逐拍重新规划 | 同左，每钟摆 advanceNPCs(1.0)，行为一致 |
| player.curS | +SCALE，取余 | 不变 |
| 适用场景 | 逐步推进，一次按键可能不触发钟摆 | 消耗固定时间，cost>1 时多次结算 |
| 选中限制 | 单人 / 多人均可 | 仅选中单个角色时可用 |

### NPC curS 累加规则

玩家行动了0.5个钟摆，钟摆全局前进0.5，npc根据0.5个钟摆，行动0.5个钟摆的动作，或移动0.5个钟摆距离。不管npc选什么，先计算能走多少格，选移动curS就加上这么多；选行动就丢弃计算的移动格子数，curS也不加
curS只是为了通过速度比值计算走一格的时间，记录是因为所有生物都可能被玩家控制，保证切换时逻辑通顺。

curS 是**实际走过的里程**，不是时间流逝的刻度。NPC 仅在 AI 决策选"移动"时才累加 curS：

```
潜在移动量 = maxS × delta       // 先算 delta 钟摆"值"多少格

选"移动":
  old_tiles = curS_ticks / SCALE
  curS_ticks += 潜在移动量 × SCALE
  crossed = new_tiles - old_tiles
  curS_ticks %= maxS × SCALE
  执行移动 crossed 格

选"攻击/技能/待机/...":
  潜在移动量 丢弃
  curS_ticks 不变   // 没走路，里程表不转
```

### 为什么用 old 做差而不用增量

仅在 NPC 选移动时适用。curS=0.79格，潜在移动=0.3格，增量法得出 0 格，但 0.79+0.3=1.09 跨过了 1.0 线 → 做差法得出 1 格。old 保留了累加前"已经跨过了几根整数线"的信息。

### delta

```
潜在移动量 = maxS × delta     // delta 钟摆能走多少格
```

| 调用位置 | delta |
|----------|-------|
| 移动路径 `tickPendulum()` while 循环体内 | 1.0 |
| 行动路径 while 循环体内 | 1.0 |

两条路径的 NPC 结算已统一——都是每 1 钟摆调用一次 `advanceNPCs(1.0)`，NPC 逐拍重新规划。
留 `delta` 参数是为了扩展性——如果未来某个机制需要一次性推进半拍或多拍（比如"加速时间流动 2 钟摆"），可以直接 `advanceNPCs(2.0)`。
